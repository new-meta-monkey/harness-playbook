Beyond the model

The Harness Playbook: Making AI Agents Production Ready

As developers, we know a strong model can reason, write code, and call tools. But when we put an agent into production, it also needs to know what it may do, prove what it did, recover safely, and hand control to a person at the right moment. The harness makes that possible.

01 · The shift

Stop treating the model as the product

The model provides reasoning. Our harness turns that reasoning into controlled work inside a real environment.

Most of us have seen the same pattern: the first demo feels magical, then production asks harder questions. Which data can it see? Which tools can it call? What happens halfway through a failed run? Who approves a risky action? Those questions are not model questions. They are engineering questions, and the harness is where we answer them.

“The model proposes. We decide what can run, what must be checked, and when a human takes over.”A developer’s production mental model

AI Engineer describes the harness as the control layer for lifecycle, shared state, permissions, conversation threads, and human approval.[1] Anthropic makes a related distinction: workflows follow paths defined in code, while agents choose their own path at runtime.[2]

  • 1
    A model answers.

    We need an agent to act through tools and keep working until the goal or a stop condition is reached.

  • 2
    A prompt suggests.

    We need the harness to enforce permissions, timeouts, approval gates, budgets, and output contracts.

  • 3
    A demo works once.

    We need traces, edge-case tests, and a habit of turning every failure into a regression check.

02 · Anatomy

Six layers that make an agent shippable

These are the layers we should be able to explain in a design review. They stay model neutral, so we can change GPT, Claude, Gemini, or a smaller model without rebuilding the product contract.

01

Context and memory

Load the smallest useful context. Separate user, task, and system state. Summarise long runs instead of sending everything again.

02

Tool contracts

Give every tool a clear name, typed input, typed output, timeout, error shape, and idempotency rule. Treat tools like internal APIs.

03

Policy and identity

Use least privilege. Keep read, write, and destructive actions separate. Put policy in code, not only in the system prompt.

04

Execution control

Set maximum steps, cost budgets, retry limits, cancellation, checkpoints, and safe resume behavior.

05

Verification

Check structure, facts, tests, business rules, and final state. A tool saying “success” is not always proof that the goal was reached.

06

Observability

Capture traces, latency, tokens, tool outcomes, policy blocks, and human overrides. Redact sensitive data before it enters logs.

03 · Runtime loop

A robust run is a controlled loop

We can let the agent choose the next step without giving up control. Our harness still owns every boundary around that choice.

One controlled agent cycleDECIDE → GUARD → ACT → PROVE

Anthropic recommends ground truth from the environment at each step, plus checkpoints and stopping conditions.[2] OpenAI also frames an agent run as a loop with explicit exit conditions, tool definitions, guardrails, and hooks.[3]

# A narrow contract is easier to trust than a powerful generic tool
tool: create_refund_request
input: order_id, reason, amount
can_read: order_status, payment_method
cannot_do: issue_refund, change_bank_account
approval: required when amount > team_limit
success_proof: request_id + persisted_status
on_unknown: stop and hand off to human
04 · Industry proof

What changes at enterprise scale

At enterprise scale, we do not improve an agent only by choosing a larger model. We narrow its operating space and raise the quality of evidence it must produce.

Real example
Google security

Specialists, structural proof, then human review

Google reports a multi-agent security harness that scans code changes, uses local threat models, validates findings with program analysis, and proposes fixes for human review. The system separates scanning, triage, and fixing so each stage can challenge the previous one.[5]

Real pattern
Agent workflows

Use autonomy only where the path is unknown

Anthropic’s production guidance starts with simple, composable workflows. Route known ticket types through fixed paths. Use an agent for open-ended coding or research where the required steps cannot be known in advance.[2]

Banking and insurance

Let the model interpret documents and detect exceptions. Let deterministic services calculate money. Require approval before payment, policy change, or customer communication.

GROUND → CALCULATE → APPROVE

Healthcare operations

Scope access by patient and purpose. Cite the source record for every summary. Block unsupported recommendations. Route clinical decisions to qualified people.

SCOPE → CITE → ESCALATE

Software delivery

Work in an isolated branch. Limit files and commands. Run build, tests, lint, security scans, and diff review. Never treat generated code as verified code.

SANDBOX → TEST → REVIEW

IT operations

Start with read-only diagnosis. Generate a change plan. Simulate when possible. Require approval for production. Verify service health after the action.

OBSERVE → PLAN → VERIFY
05 · Delivery playbook

How we can practise harness engineering

As developers in IT services, we should build reusable controls once, then configure them for each client, domain, and risk level.

  1. Define the job and the stop condition

    Write what the agent may achieve, what is out of scope, and what proof means “done”. Prefer a workflow when steps are known.

  2. Classify every tool by risk

    Read tools can run automatically. Writes need stronger validation. Irreversible or external actions need human approval.

  3. Use client specific policy packs

    Keep retention, PII handling, geography, approval limits, and allowed systems outside the prompt. Version them like code.

  4. Create a golden evaluation set early

    Include normal tasks, incomplete inputs, conflicting instructions, permission failures, tool timeouts, and prompt injection attempts.

  5. Trace the whole run

    Google’s guidance calls for logs, metrics, and traces across model calls and tools.[4] Add business outcomes such as task completion and human correction rate.

  6. Turn incidents into permanent improvements

    Add each failure to regression tests. Then fix the right layer: context, tool contract, policy, verifier, or recovery path.

  7. Prove model portability

    Run the same evaluations across model versions. Choose by quality, latency, cost, and risk. Do not make model brand the architecture.

06 · Companion lab

Make the difference visible in one small repo

If we want other developers to feel the difference, we should run the same task twice. The model and prompt stay similar. Only the harness changes.

Version A: SDK call only

A minimal Anthropic SDK script answers a request and can call one tool.

  • API key comes from an environment variable.
  • No input schema beyond the prompt.
  • No tool permission check.
  • No bounded retry or success proof.
  • Useful for learning, not production.
VS

Version B: same agent, harnessed

The same task runs through a small, readable control layer.

  • Typed input and output validation.
  • Allowlisted tool with a risk level.
  • Step limit, timeout, and retry budget.
  • Approval gate before a write.
  • Structured trace and deterministic verifier.

The example we would build: we ask both versions to read a sample service incident, inspect a small local knowledge base, and prepare a remediation plan. Version B must cite the evidence it used, reject prompt injection inside the incident text, and stop before any simulated production change. That gives our teammates something concrete to run, break, and discuss.

  • 01-without-harness/ shows the short SDK-only path and its limits.
  • 02-with-harness/ adds policy, tool contracts, verification, tracing, and recovery.
  • tests/ contains happy path, tool failure, permission denial, malformed output, and prompt injection cases.

07 · Design review

The 10 minute harness review

This is the quick review we can run together before a pilot, a client demo, or a production change.

Production readiness checklist

  • The goal, scope, owner, and stop condition are explicit.
  • Each tool has typed inputs, typed outputs, and clear errors.
  • Credentials and data access follow least privilege.
  • External and irreversible actions require approval.
  • Retries are bounded and duplicate actions are prevented.
  • Long runs have checkpoints, cancellation, and safe resume.
  • Outputs are verified against source systems or deterministic checks.
  • Traces capture decisions, tool calls, latency, cost, and policy events.
  • Sensitive values are redacted from prompts, traces, and logs.
  • Known failures are part of a versioned evaluation suite.

Our competitive edge is not just a smarter model.

It is the harness we build around it: the layer that makes good behaviour repeatable, bad behaviour visible, and risky behaviour controllable. When that layer is built well, every model upgrade becomes safer to adopt.
